01 / What you are building

One recipe. A different model for each person.

The extraction prompt is the recipe you design. The user model is the personal description that recipe produces from someone’s choices. Neither is the research agent itself.

InputA person’s history →

Contexts, two responses, and which one they preferred.

You design thisExtraction recipe →

An LLM uses your prompt to infer a few conditional preferences.

Saved outputPersonal principles →

Small, readable claims with supporting examples and limits.

TestPredict a new choice

Another LLM call gets the principles and new options, without the answer.

Highest-leverage next move: inspect the two real histories here, revise one extraction prompt, then compare its predictions against no history and raw history. Treat the extractor as a hypothesis until the comparison supports it.

What comes from PRISM?

Observed choices from public participants. These let us test the recipe without first collecting a new research dataset. A model of prism:user476 is a model of that participant—not a model of Gio.

What you provide: the extraction instructions, a review of what the resulting principles mean, and the rule for deciding whether to use them.

What plugs into the team?

Task B supplies choices or other evidence about the actual researcher. Task A provides the reusable fitting and prediction method. Task D uses the fitted model to rank research options and feed principles to the proposer.

Task C measures eval awareness and validity. Task E runs comparisons and builds the demo. Taste does not get to overrule evidence.

PRISM versus Arena, and what normalization changes
They are different source datasets released in a shared PersonalRewardBench format. We use the curated PRISM version here. The common fields are user ID, conversation ID, context, preferred response, rejected response, and split.
Our adapter preserves the text and partitions, gives users and conversations namespaced IDs, and deterministically shuffles the options to A/B (seed 0 here). It strips upstream model predictions and reasoning. The target answer is kept for evaluation; it is never part of a new prediction’s input.
The project audit found 12 duplicate pairs in the full raw PRISM release. Gio approved removing agreeing duplicates and recording each removal. These two embedded history subsets contain no duplicate pairs under that policy. A reproducible full-data manifest remains an experiment prerequisite.





 03 / The part you own
Edit the recipe, not each person’s answer.

 
This is a proposed minimal extractor. One LLM call reads one person’s labeled history and returns at most five principles. We have not established that this beats raw history. The same recipe must work for every evaluated person.

 

 
What to change first
Level of abstraction. “Always be concise” may fail when detail is needed. “For practical requests, favor focused steps over unrelated extras” is conditional, but still needs support.
Evidence bar. A single pair can suggest a rule. Repeated choices across conversations make the inference more credible. Allow an empty profile when evidence is weak.
Scope. Preferences describe likely choices. They do not establish facts, endorse the person’s beliefs, or tell the research loop to relax validity checks.
Do not tune to the answer. Develop the recipe using development users only. Freeze it before the final users are evaluated.
This editor is local. It does not run a model, spend credits, or replace an existing method. “Preview” assembles a proposed request using all embedded history for the selected person.

 
Exact proposed request

 
Why try this before a larger method search?
It is cheap to inspect and easy to falsify. Raw history is the strongest simple alternative: it keeps nuance that a summary can lose. More complex hypothesis search or validation filtering could help, but adds calls and more chances to fit noise. Start with this comparison; expand only when the error analysis gives a specific reason.
The current M2 and M3 implementations have multiple stages. This proposed one-call recipe is a new simplification, not a claim that those implementations or their source papers work this way.





 04 / Inspect the proposed output
A user model is a set of testable guesses.

 
The output should help decide between new options. Store a small JSON record for traceability; render the conditional principles as natural language in the predictor’s context. No vector database or training job is required for this proposal.

 
No model output has been generated here. The draft below is hand-written to illustrate the format, using one actual history pair. It is not a learned profile, a validated rule, or a finding about the full person.

 
What each field is for
when: the situations where the rule might apply.
prefer: a tradeoff that distinguishes options.
evidence_ids: which observed pairs support the guess.
limits: competing explanations or cases where the rule may fail.
unresolved: gaps worth testing, rather than details to invent.
The structure checker checks JSON shape and evidence IDs only. It cannot tell whether a principle is true or useful. This draft schema needs an adapter before it can be loaded as the repository’s saved user model.

 
Gio’s review: could this rule make a useful prediction?

 
How this text changes the next model call
Predict which response this person would prefer.
Treat their inferred preferences as fallible context.

PERSONAL PRINCIPLES: [the extracted conditional rules]
NEW CONTEXT: [a held-out conversation]
OPTIONS: [response A, response B]

Return probabilities for A and B, plus a short rationale.
Do not receive the held-out choice label.
For the research loop, the same contract takes research decision context and candidate actions instead of chat responses. The interface transfers; its accuracy may not. That is a separate empirical question.





 05 / Evidence, not an attractive profile
Does it predict choices it has not seen?

 
A profile can sound insightful and add nothing. Evaluate all three conditions on the same people and held-out conversations, using the same predictor model and option ordering.

 
ConditionPredictor seesQuestion it answers
M0 · No historyNew context + optionsHow much can a generic model already predict?
M1 · Raw historySame new input + that person’s labeled historyDoes personal history help without extraction?
Proposed extractorSame new input + principles derived from that exact historyDoes compression preserve or improve useful personal information?

 
Two split boundaries
Across people: development → finalUse development users to choose the recipe. Freeze the recipe and settings before opening final-user targets.
Within each person: history → held-out conversationsFit their profile from history. Judge its predictions on other conversations. Keep every pair from one conversation in the same partition.
Existing methods may use inner validation too; declare that explicitly and give comparisons the same allowed information. The first simple extractor proposed here uses history only. Do not mistake a final user’s allowed history for their protected target labels.
What to report
  • User-average accuracy: compute each person’s accuracy, then average those values.
  • Paired improvement: compare methods on the same users; show a confidence interval resampling users together.
  • Cost and failures: include extraction, prediction, and failed calls. Failures must not disappear from the denominator.
  • Scope: number of people, conversations, choices, model, prompt version, split manifest and code version.

 
Actual PRISM results
No live comparison recorded yet. There is no winning method to display. The Arena smoke test does not fill this gap.
Before the next run: finish and verify the deduplicated manifest, freeze a bounded development batch and model, estimate calls, and agree its budget. The earlier $1 approval covered the completed tiny pilot.

 
Decision rule: how to interpret the result
Observed resultWhat we should do
Extractor clearly beats raw historyKeep it as the leading candidate; confirm once on final users after freezing the design.
Similar accuracy, lower costPotentially useful compression. Report uncertainty; do not claim superiority or equivalence from a small, noisy sample.
Raw history winsUse raw history for prediction. Investigate which information extraction lost; do not add complexity without a specific hypothesis.
No personal method beats M0History may be too sparse, the recipe may fail, or the task may reward generic response quality. Report that limit.
Optional next control: swap profiles across people. If the correct person’s profile works no better than a mismatched one, the gain may come from generic advice rather than personalization. A small noisy comparison cannot settle this by itself.

 
Two separate claims. PRISM can test preference prediction across held-out conversations. It cannot establish that Gio’s overnight research runs improve. That second claim needs Task B’s researcher data and Task D’s controlled comparison, with Task C’s validity checks.

 
Confidence and M7: the unresolved limit
Gio chose to defer calibrated M7 because the current per-user split does not support it. Raw model probabilities are uncalibrated; “0.8” does not yet mean 80% empirical reliability.
The adviser currently has a confidence threshold, but does not enforce the model’s calibrated flag. Before relying on confidence-based routing, agree with Task D how uncalibrated outputs are handled. Do not present an arbitrary threshold as a proven safety gate.
